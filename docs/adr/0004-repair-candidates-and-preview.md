# 乱码修复：候选生成 + 预览裁决，而非自动判定

现有转换管线要求文件是**单一编码**：探测链对"混合编码"或"字节合法但内容是乱码"的文件一律判 low-confidence 跳过（ADR-0003 的刻意结果）。新增 `Repair Encoding` 命令填补这一空白，但它面对的是本质上**有歧义**的问题——同一段字节可能被多种编码"解通"。决定：核心 `proposeRepairs` 只负责**生成候选**（两族），按可信度评分排序，**绝不自动选定并写盘**；最终由强制预览 + 用户选择裁决。这把 ADR-0003"探测提出假设、解码器验证"的立场再推一环——最后的验证交给人眼。

两族候选：

- **Mojibake 逆向**：文件能被单一编码严格解码，但文本是乱码（`锟斤拷`、`Ã©Â¸`、`浣犲ソ`）。对预设编码对 (误读编码, 正确编码) 做 `text.encode(误读).decode(正确)`，双向严格校验（重编码须无损、结果须严格可解），并排除恒等结果与"评分不高于原乱码"的候选。
- **混合分段**：文件含主编码非法字节（如 UTF-8 源码里夹了 GBK 注释）。以 ASCII 为界切分，每个**极大非 ASCII 段**先整体试 UTF-8，失败再试副编码。**整体判定而非逐字节贪心是关键**：GBK 的 `D1A1`「选」恰好也是合法 UTF-8 双字节序列 `U+0461`「ѡ」，逐字节走会把它误当 UTF-8 吞掉；要求整段合法才认 UTF-8，段内其余非法字节就能把判定逼回副编码。

## Consequences

- 正常文件误触发修复也会产生候选，但"更差即丢弃"过滤 + 强制预览使其无害：用户不选即不改一字。
- 两个已知天花板，均 **fail-safe**（无法生成合理候选 → 不写盘）：① 外来段与合法非 ASCII 的 UTF-8 文本无 ASCII 分隔相邻时，被当作单段判定；② 副编码字符的尾字节落在 ASCII 区（GBK 尾字节 `0x40–0x7E`）会切断该段，使其在两编码下都解不通。升级路径：完整 UTF-8 状态机 + 逐段编码投票。
- **不可逆损坏无能为力**：若字节已被破坏（全角分号 `EF BC 9B` 被改成 `EF BC 3F`、或文本已丢失为 `?`/U+FFFD），原始信息在字节层已不存在，任何解码都无法还原——这只能靠版本控制。此时命令如实报告"未发现可自动修复的乱码"，而非猜测写盘。
